# Plan 模式处理指南

## 概述

本指南定义了 `junsi-dev-toolkit` 在 Plan 模式下的统一处理策略。所有子工具在检测到 Plan 模式时，应遵循本指南。

## Plan 模式对 Skill 的影响

Plan 模式与"验证驱动型 Skill"存在根本冲突：

| 维度 | Plan 模式默认行为 | Skill 实际需求 |
|:---|:---|:---|
| 执行方式 | 一次性生成完整步骤清单 | 迭代循环（写 → 编译 → 诊断 → 改 → 再编译） |
| 错误处理 | 预设步骤，失败时卡住 | 动态诊断，根据错误调整 |
| 验证 | 计划"测试将通过" | 实际运行，失败则进入诊断 |
| 上下文 | 步骤间上下文可能断裂 | 需要连续上下文追踪问题 |

## Plan 模式检测

子工具应在开始执行时检测 Plan 模式：

**检测信号：**
- 系统提示"计划模式已启用"
- 用户明确说"帮我创建一个计划"
- 当前存在未执行的 Plan 步骤列表
- 你正准备调用 `plan_create` 工具

**如果检测到 Plan 模式，子工具必须：**

### 第 1 步：向用户发出警告

```markdown
⚠️ **Plan 模式影响提示**

当前子工具 `[子工具名]` 依赖迭代验证循环。Plan 模式可能导致：
- 编译失败后无法动态调整
- 验证结果不符合预期时无法自动进入诊断
- 上下文断裂导致诊断不准确

**建议**：关闭 Plan 模式后重试。
**如坚持使用**：我将采用"单步 Plan"降级策略。
```

### 第 2 步：降级策略执行

如果用户坚持使用 Plan 模式，子工具必须：

1. **Plan 粒度限制为 1 个原子操作**（如"修改 X 文件"）。
2. **禁止在 Plan 中预测结果**（不写"编译将通过"）。
3. **验证和诊断在 Plan 外部动态执行**。
4. **每轮 Plan 不超过 3 步**。
5. **如果编译/测试失败，立即暂停 Plan，触发诊断流程，修复后再继续**。

### 第 3 步：禁止事项

在 Plan 模式下，子工具禁止：
- 一次性规划完整的"修复→编译→测试"流程
- 在 Plan 中写入"如果失败则..."的条件分支
- 跳过验证步骤因为"Plan 里没写"
- 在 Plan 中承诺"测试将通过"
