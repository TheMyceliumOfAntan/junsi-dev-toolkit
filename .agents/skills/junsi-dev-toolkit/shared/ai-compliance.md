# AI 服从性指引

## 通用原则

| ✅ 必须做 | ❌ 禁止 |
|----------|--------|
| 先理解需求/问题再动手 | 看到关键词直接开写 |
| 遵守 AGENTS.md、opencode.md、CLAUDE.md | 技能覆盖项目自有规范 |
| 改完代码更新 docs/ 和 AGENTS.md | 改完不更新文档 |
| 每个验证步骤**实际执行命令并粘贴输出** | 说"验证通过"但不粘贴实际结果 |
| 改动最小化，只改需求指定的 | 顺手重构无关代码 |
| 复用项目已有库/工具/模式 | 凭臆想引入新依赖 |

## 用户提出修改意见时（适用所有技能）

**这是 AI 最常见的违规场景。** 用户看完方案说"改一下"，AI 直接改代码不更新方案：

1. **先停下**。不要立即改代码。
2. **更新方案/计划描述**，反映用户的修改意图。
3. **输出更新后的方案，问用户"这样可以吗？"**
4. **用户确认后才改代码。**

🔴 禁止：用户提了意见 → 你直接改代码（跳过了方案更新和确认）。

## 需求开发（RDD）

| ✅ 必须做 | ❌ 禁止 |
|----------|--------|
| 零模糊点才出方案：还有任何一个问题未回答就不得出方案 | 心有疑惑就开始写 |
| 至少提 2 种方案及优缺点 | 只给 1 种 |
| 用户确认方案后才写代码 | 边问边改、边改边问 |
| 改代码前先 git stash 或 commit checkpoint | 不 checkpoint 直接改 |
| 验证场景必须实际运行并粘贴输出 | 说"看起来没问题"代替实际运行 |
| 编译通过要继续验证逻辑正确性 | 编译通过就声称做完了 |
| 每改一步更新 todo 状态 | 全部写完才验证 |

## Bug 修复（Diagnose）

| ✅ 必须做 | ❌ 禁止 |
|----------|--------|
| 先理解问题所有上下文 | 看到报错直接改代码 |
| 枚举至少 2 个具体原因（含代码位置） | 只列一个就动手 |
| 列完原因等用户确认再改 | 列原因的同时把代码也改了 |
| 改代码前先 git stash 或 commit checkpoint | 改了再后悔无法回滚 |
| 原始场景复测必须**粘贴实际命令输出** | 说"已复测通过"但不附输出 |
| 复测通过才能声称修好 | 编译通过就声称修好了 |

## 代码移植（Migrate）

| ✅ 必须做 | ❌ 禁止 |
|----------|--------|
| 先扫描源+目标项目再动手 | 不了解目标架构就开始移植 |
| 发现冲突先问用户 | 默认覆盖目标已有功能 |
| 生成 MAPPING_TABLE.yaml 固化映射 | 靠记忆做映射 |
| 每原子包 ≤200 行变更 | 一次移植整模块不拆分 |
| 移植中发现的 bad smell 记录到 ADR | 当场重构或直接忽略 |
| 快照自动比对 | 肉眼对比输出 |

## 验证输出规范

任何时候你声称"验证通过"时，必须同时满足：

1. **你实际执行了命令**（不是肉眼检查，不是 grep 代码）
2. **你粘贴了命令的输出**（至少关键行）
3. **你明确说了"符合预期"或"不符合预期"**（不是含糊的"看起来还行"）

🔴 违反此规范的响应将被视为"未验证"。
