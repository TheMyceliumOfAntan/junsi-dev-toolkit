# AI 服从性指引

集中管理所有技能通用的"该做什么、不该做什么"。使用正面指令，减少说教感。

## 通用原则

| ✅ 应该 | ❌ 不应该 |
|---------|----------|
| 先理解需求/问题再动手 | 看到关键词直接开写 |
| 遵守 AGENTS.md、opencode.md、CLAUDE.md 中的硬性要求 | 技能覆盖项目自有规范 |
| 及时更新 docs/ 和 AGENTS.md（架构/API/模块变更时） | 改完代码不更新文档 |
| 每个验证步骤实际执行（build/lint/test） | 肉眼检查代替实际运行 |
| 改动最小化，只改需求指定的部分 | 顺手重构无关代码、加未要求的"优化" |
| 复用项目已有的库/工具/模式 | 凭臆想引入新依赖或风格 |

## 需求开发（RDD）

| ✅ 应该 | ❌ 不应该 |
|---------|----------|
| 先澄清需求，零模糊点再出方案 | 心有疑惑就开始写代码 |
| 至少提 2 种方案及优缺点 | 只给 1 种方案 |
| 用户确认方案后才写代码 | 边问边改、边改边问 |
| 拆解为可独立验证的步骤 | 一步改完所有文件 |
| 每完毕一步更新进度并验证 | 全部写完才验证 |

## Bug 修复（Diagnose）

| ✅ 应该 | ❌ 不应该 |
|---------|----------|
| 先理解问题所有上下文 | 看到报错直接改代码 |
| 枚举至少 2 个具体原因（含代码位置） | 只列一个就动手 |
| 列完原因等用户确认再改 | 列原因的同时把代码也改了 |
| 原始场景复测通过才算修好 | 编译通过就声称修好了 |
| 修改前 git stash 或 commit checkpoint | 改了再后悔无法回滚 |

## 代码移植（Migrate）

| ✅ 应该 | ❌ 不应该 |
|---------|----------|
| 先扫描源+目标项目再动手 | 不了解目标架构就开始移植 |
| 发现冲突时询问用户覆盖还是共存 | 默认覆盖目标已有功能 |
| 生成 MAPPING_TABLE.yaml 固化映射 | 靠记忆做映射 |
| 每原子包 ≤200 行变更 | 一次移植整模块不拆分 |
| 移植中发现的 bad smell 记录到 ADR | 当场重构或直接忽略 |
| 快照自动比对结果 | 肉眼对比源和目标输出 |

## 通用陷阱

- **编译通过 ≠ 逻辑正确** — 必须实际运行验证场景
- **grep/阅读代码 ≠ 验证** — 必须实际执行命令
- **测试不只是"建议"** — 提议测试场景并执行
- **改动很小也要 build** — DI 注入可能拼错接口名
- **一次只改一个变量** — 改多个地方同时测，出错了无法定位
