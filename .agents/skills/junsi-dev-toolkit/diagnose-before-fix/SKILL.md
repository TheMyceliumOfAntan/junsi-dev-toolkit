# Diagnose Before Fix

## ⛔ 互锁门禁（与其它 Skill 的边界）

本 Skill 与以下 Skill 互斥，按优先级触发：

| 优先级 | 触发条件 | 执行 Skill |
|:---|:---|:---|
| 最高 | 用户说"移植/迁移/migrate/port" | `code-migrater`（其他 Skill 静默） |
| 次高 | 用户说"报错/不对/不工作/返回错误/显示不对/空列表"等不符合预期的行为 | `diagnose-before-fix`（若同时含"移植"关键词，让位于 code-migrater） |
| 最低 | 用户说"添加/新增/实现一个新功能" | `requirements-driven-dev`（若同时含"修/不对/报错"，让位于 diagnose-before-fix） |

**纯知识问答（如"这个 API 怎么用"）不触发任何 Skill。**

## 概述

修复代码问题前，必须先诊断、枚举所有可能原因、与用户确认方向，再动手。修复后必经实际运行验证（优先复现原始场景），验证失败则重新诊断，思路有误则推翻重来。

**核心原则：诊断不足的修复比不修复更危险。**

## 触发条件

**以下任一情况出现时，必须触发此 Skill：**

| 用户说了什么 | 示例 | 是否触发 |
|:---|:---|:---|
| 直接贴了报错日志/堆栈/crash 报告 | 贴了一段 Exception、stack trace | 触发 |
| 说了"结果不对/返回错了" | "接口返回的数据不对"、"计算结果和预期不一样" | 触发 |
| 说了"报错了/有错误" | "这个 API 返回了 500"、"返回了错误码" | 触发 |
| 说了"点了没反应/没效果" | "点击按钮没反应"、"提交后没跳转" | 触发 |
| 说了"显示不对/页面乱了/白屏" | "这个字段显示为空"、"页面乱了" | 触发 |
| 说了"不工作/有问题/出错了" | "下载不工作"、"这个功能有问题" | 触发 |
| 说了"返回空列表/没有数据" | "接口返回了空列表"、"查询不到数据" | 触发 |
| 说了"怎么办/怎么解决"且伴随具体问题描述 | "这个报错怎么解决"、"这个结果不对怎么办" | 触发 |
| Build/Test/CI 失败 | "npm run build 报错了" | 触发 |

**不触发的情况：**
- 纯知识问题："这个 API 怎么用？"（走普通对话）
- 纯新功能需求："帮我加一个登录功能"（走 `requirements-driven-dev`）
- 纯移植需求："把这个项目从 Vue2 迁到 Vue3"（走 `code-migrater`）
- 用户明确说"只帮我看原因，不用改代码"（可简单分析，不走完整修复流程）

## 核心流程

### 强制契约：与项目知识中枢（project-docs MCP）的交互

**执行前：上下文已由路由器通过 MCP 注入**

路由器已在分发前调用了 `project-docs.query_docs`，相关文档摘要已包含在输入中。

如果未收到注入的上下文：
1. 主动调用 MCP 工具 `project-docs.query_docs`，关键词根据当前任务提取。
2. 使用返回结果作为上下文。

**执行后：必须通过 MCP 写回**

任务完成后，必须调用 `project-docs` MCP 工具更新文档：

| 场景 | 调用的工具 | 说明 |
|:---|:---|:---|
| 新增了架构决策 | `create_adr` | 记录决策 |
| 新增/修改了 API | `update_doc` | 更新 API 规范 |
| 新增了模块 | `update_doc` | 更新模块划分 |
| 新增了 UI 组件 | `update_doc` | 更新组件设计规范 |

**违反此契约视为违规，任务不计为完成。**

### 模式检测（第一步）

检测当前处于 Plan 模式还是 Build 模式。

#### 如果在 Plan 模式下：

**你的职责是：分析问题 → 输出计划 → 指引切换**

不要尝试修改文件或运行命令。执行以下步骤：

1. 读取用户描述的问题和相关代码。
2. 理解问题，分析数据流转路径。
3. 枚举所有可能原因（≥2个，引用具体代码位置）。
4. 呈现分析结果，询问用户确认方向。
5. **输出详细的执行计划**，包括：
   - 将修改哪些文件（具体路径）
   - 每步修改什么内容
   - 修改后的验证步骤
   - 预期的验证结果
6. **在计划末尾输出模式切换指引**（参见 `../shared/mode-switch-guide.md`）。

**⚠️ 关键**：完成以上步骤后，停止。等待用户切换到 Build 模式。

#### 如果在 Build 模式下：

直接按以下原流程执行，无需额外步骤。

---

严格按以下步骤执行，不可跳过或调换顺序。

**关键纪律：**
- 步骤 5（Build）和步骤 6（原始场景复测）与步骤 1-4 同等强制，不是"建议"或"可选"
- **在步骤 6 原始场景复测通过之前，修复不算完成**
- **未走完 8 步之前，禁止 commit、禁止 push、禁止声称"修复完成"**
- 只跑 grep/阅读代码不算测试——必须实际执行 build 命令和实际运行验证

### Git Checkpoint 机制

每次修改代码涉及以下操作时，必须创建 checkpoint，确保随时可回滚：

**创建 checkpoint 的时机：**

| 时机 | 操作 | 用途 |
|------|------|------|
| 步骤 3 确认方向后、步骤 4 改代码前 | `git stash` 或 `git commit --allow-empty -m "checkpoint: 修复前快照"` | 回滚到修改前的干净状态 |
| 步骤 4 中每次阶段性修改完成后 | `git add -A; git commit -m "checkpoint: [简述本次改动]"` | 分步回滚到中间版本 |
| 步骤 8 决定推翻重来时 | `git reset --hard <checkpoint-hash>` | 回到修改前或某个中间 checkpoint |

**Checkpoint 纪律：**
- 步骤 4 开始前**必须先创建 checkpoint**（记录修改前状态）
- 每个 checkpoint commit message 以 `checkpoint:` 为前缀，与正式 commit 区分
- 步骤 8 推翻重来时，使用 `git log --oneline` 找到 checkpoint，然后 `git reset --hard` 回滚
- 回滚后重新从步骤 2 开始诊断，之前的错误方向不复存在
- **最终修复验证通过后**，可以 squash 所有 checkpoint 为正式 commit（用户要求时再执行）

### 1. 理解问题（不碰代码）

- 仔细阅读用户描述的错误信息、日志、堆栈追踪
- 阅读相关代码，理解其设计意图
- **检查近期改动**：`git log --oneline -20` + `git diff HEAD~3 -- <相关目录>` 查看最近哪些提交可能引入了问题。新依赖、配置变更、环境差异往往是根因
- **此阶段禁止任何代码编辑**

**无日志时的上下文收集（当用户未提供错误日志时）：**
- 询问用户**实际发生了什么** vs **预期发生了什么**。
- 询问**操作步骤**（按什么顺序、点了什么、输入了什么）。
- 若涉及前端：让用户打开 F12 → Network 查看请求参数和响应；Console 是否有警告或报错。
- 若涉及后端：用 curl/Postman 实际调用接口，确认返回结果。
- 收集足够信息后，进入步骤 2（枚举可能原因）。

### 2. 枚举所有可能原因

**必须将分析结果显式输出给用户**，不可在脑中过一遍就跳过。格式：

```markdown
## 可能原因分析

1. **[原因 A]**（可能性：高）— 说明为什么（引用具体代码位置）
2. **[原因 B]**（可能性：中）— 说明为什么
3. **[原因 C]**（可能性：低）— 说明为什么
```

- 至少列出 2 个具体、可验证的原因（不能是"代码逻辑错误"这种泛泛之谈）
- 每个原因需引用具体代码位置或错误信息作为依据
- 如果只想到一个，换个角度再想想

**辅助技巧：模式对比分析**

在枚举原因时，如果代码库中存在类似功能且正常工作的代码，做对比：

1. 找到功能相似、能正常运行的代码（同一个项目中的同类实现）
2. 对比两者差异：注册方式、初始化顺序、依赖注入、配置项、调用路径
3. 列出所有差异点，不管看起来多小——"这个不可能有关系"往往是真凶
4. 把差异点作为补充原因加入分析列表

示例：
```
## 模式对比

对比「正常工作的 LauncherDownloadService」vs「有问题的 JavaDownloadService」：
- LauncherDownloadService 在 ProgressSseEndpoints 中注入 ✓
- JavaDownloadService 在 ProgressSseEndpoints 中未注入 ✗ ← 差异点
```

### 3. 询问修复方向

将分析结果呈现给用户，询问：

- 倾向于哪个原因？
- 修复方向是否有特殊要求？
- 是否有额外的上下文或约束？

**在用户明确回复确认方向之前，不写任何修复代码。** 不允许"我倾向于 X，同时先改着"这种边问边改的行为。

**如果你在同一个回复中既问了方向又改了代码，等于没问。** 问完方向后，必须停手，等用户下一轮回复，再进入步骤 4。

### 4. 实施修复

**修改前必须创建特性分支：** `git checkout -b fix/[问题简述]`

```bash
# 示例
git checkout -b fix/java-download-progress
```

**然后创建 checkpoint：** `git stash`（或 `git add -A && git commit -m "checkpoint: 修复前快照"`）。

按用户确认的方向修改代码。改动遵循：
- 最小化原则：只改必要的部分
- 不顺手重构无关代码
- 匹配现有代码风格
- **单变量验证**：一次只改一个因素，改完 build 验证通过后再改下一个。不要一次改多个地方然后一起测——出错了无法定位是哪个改动导致
- 每次阶段性修改完成后创建 checkpoint：`git add -A && git commit -m "checkpoint: [改动简述]"`

**所有 checkpoint 提交留在特性分支上，不进入 main。**

**修改时写入临时调试日志：**
- 在关键路径（入口参数、中间计算结果、出口返回值）插入日志输出
- 使用项目已有的日志框架（如 `ILogger`、`Console.WriteLine`、`println!` 等），匹配现有日志风格
- 日志以明显标记前缀区分，便于后续清理，例如：`[DEBUG-FIX] 收到请求: param=xxx`
- 日志内容包含：时间点、变量值、路径分支、异常信息
- **多组件/多层系统**：在每个组件边界（输入/输出）打桩，跑一次即可定位问题发生在哪一层

### 5. Build 验证

修复后立即 build 项目，确认无编译错误。

- 使用项目的 build 命令（如 `dotnet build`、`npm run build`、`cargo build` 等）
- 有编译错误则修复后重新 build，直到通过
- Build 失败不能进入下一步
- **对于解释型语言**（Python、JavaScript 等）：运行 lint/typecheck/语法检查作为等效验证（如 `ruff check`、`tsc --noEmit`）

### 5b. API 端点验证（涉及后端接口时必须执行）

如果修改涉及后端网络 API（REST 端点、SSE、WebSocket 等），Build 通过后必须实际调用接口验证返回结果。

**自主可测时（有 curl/httpie 等工具可用）：**
```bash
# 示例：直接调用修改的端点
curl -s http://localhost:5000/api/xxx | ConvertFrom-Json  # PowerShell
curl -s http://localhost:5000/api/xxx | jq .               # bash
```
- 查看响应状态码、响应体是否符合预期
- 查看服务端日志输出（含步骤 4 加入的 `[DEBUG-FIX]` 日志）
- 输出请求和响应的完整内容，与预期对比

**自主不可测时（无运行环境、需要认证、依赖外部服务等）：**
- 明确告知用户：需要手动测试哪些端点、用什么参数
- 提供测试命令或 curl 示例让用户直接复制运行
- 要求用户粘贴：**响应结果 + 服务端日志输出**

**验证结果处理：**
- 响应正常且日志符合预期 → 进入步骤 6
- 响应异常 → 根据日志定位问题，回到步骤 4 调整
- 日志与预期不符 → 分析是代码逻辑问题还是日志位置不对，回到步骤 4

### 6. 原始场景复测（强制性，非建议）

**此步骤优先于编写单元测试。** 必须先证明原始 bug 在当前代码下已被消除。

**6.1 复现路径确认**
- 回顾用户最初报告问题时描述的操作步骤、输入参数、环境条件。
- 若有模糊之处，**必须向用户确认**："您当时具体是怎么操作的？输入了什么数据？"

**6.2 实际执行复测（需启动服务时引用 `../shared/services.md`）**

若验证涉及后端 API：
- 检查服务是否已在运行（端口检测）。
- 若未运行，使用 `../shared/services.md` 中的**标准操作流程**启动服务。
- 等待健康检查通过后，再执行验证命令。
- 验证完成后**必须清理服务进程**（除非用户要求保持）。

**禁止行为**：
- 禁止在前台启动服务阻塞会话。
- 禁止不等待健康检查就发送请求。
- 禁止验证完成后不清理服务。

**6.3 输出验证（不报错 ≠ 正确）**
- 若问题是"返回了空列表"，则验证时确认**列表内有数据、数据字段完整**。
- 若问题是"计算结果不对"，则验证时输出计算结果并与预期比对。
- 若问题是"页面显示错误"，则确认 DOM 结构/文本显示正确。

**6.4 记录验证结果**
将复测结果写入 `VERIFICATION_LOG.md`：
```markdown
## 复测记录
- 复测时间: [timestamp]
- 复测命令/操作: [具体命令或操作步骤]
- 实际输出: [粘贴完整输出]
- 预期输出: [粘贴预期]
- 结论: ✅ PASS / ❌ FAIL
```

**6.5 失败处理**
若复测 FAIL（仍报错、返回仍不对、页面仍异常）：
- **立即回到步骤 2（重新枚举可能原因）**，不继续往下走。
- 禁止以"再改一个小地方就好"为由跳过重新诊断。

### 7. 测试验证（补充）

原始场景复测通过后，**主动提出**额外测试点覆盖边界和回归：

```markdown
## 建议测试点

1. **[场景描述]** — 输入: `...`，预期输出: `...`
2. **[边界场景]** — 输入: `...`，预期输出: `...`
```

同时**询问用户**测试代码应放在哪个文件/目录。不要自作主张选择位置。

执行测试并对比预期，输出结果。

### 8. 结果处理

```
digraph result_handling {
    "原始场景复测通过？" [shape=diamond];
    "修复完成" [shape=box];
    "输出不符合预期？" [shape=diamond];
    "修复思路本身有问题？" [shape=diamond];
    "回到步骤 2，重新诊断" [shape=box];
    "回到步骤 4，调整实现" [shape=box];

    "原始场景复测通过？" -> "修复完成" [label="是"];
    "原始场景复测通过？" -> "输出不符合预期？" [label="否"];
    "输出不符合预期？" -> "修复思路本身有问题？";
    "修复思路本身有问题？" -> "回到步骤 2，重新诊断" [label="是"];
    "修复思路本身有问题？" -> "回到步骤 4，调整实现" [label="否（小调整即可）"];
}
```

- 输出不符合预期 → 分析是思路问题还是实现细节问题
- **思路有问题 → 果断推翻**：`git log --oneline` 找到修改前 checkpoint，`git reset --hard <hash>` 回滚，回到步骤 2 重新诊断
- 实现细节问题 → 调整代码，创建新 checkpoint，回到步骤 5

**3 次失败上限规则：**

- 同一个问题尝试修复 **< 3 次**：回到步骤 2 重新分析，每次带着新的诊断信息
- **≥ 3 次仍失败**：停止修代码，改为讨论架构

```
第 3 次失败时的行为模式（意味着架构问题而非逻辑 bug）：
- 每次修复都暴露了新的关联问题/共享状态/耦合
- 修复需要"大规模重构"才能实施
- 每次修复在别处引入新问题

此时应：
1. 停止写代码
2. 向用户提出：当前设计是否存在根本性问题？
3. 讨论是否应该重构模式而非继续修补症状
```

这不是"假设错了"，这是"模式错了"。

### 修复完成的定义（硬性清单）

以下 **全部** 满足才算修复完成：

- [ ] 修改前已创建 checkpoint（可回滚）
- [ ] 代码已修改且用户确认方向
- [ ] Build 实际执行且通过（不是 grep、不是肉眼检查）
- [ ] 涉及后端 API 时，已实际调用端点验证返回结果
- [ ] **原始场景复测通过**：用与用户报告问题时完全相同的操作/输入/参数，实际运行一次，问题不再复现
- [ ] **输出正确性验证通过**：不仅"不报错"，还要确认返回/展示的内容符合业务预期
- [ ] 已向用户提供**可复现的验证步骤**（如：调用 X 接口传入 Y 参数，预期返回 Z）
- [ ] 用户确认结果
- [ ] **临时调试日志 `[DEBUG-FIX]` 已全部清理**
- [ ] checkpoint 提交已 squash，分支已合并到 main（或提 PR 等待 review）
- [ ] **特性分支已删除：** `git branch -d fix/xxx`

**以上任何一项未完成，禁止 commit、禁止 push、禁止说"修好了"。**

## 常见违反行为与合理化借口

| 行为 | 借口 | 现实 |
|------|------|------|
| 看到问题直接改代码 | "问题很明显" | 明显的诊断也可能遗漏备选原因 |
| 脑中分析但不输出给用户 | "我已经想清楚了" | 用户看不到你的推理，无法纠正误判 |
| 只提一种原因 | "最可能就是它" | 遗漏的 20% 可能是浪费数小时的根源 |
| 列出原因后不等确认就动手 | "显然选这个" | 用户可能有你没意识到的约束 |
| 修完不 build | "改动很小不会错" | 再小的改动也可能引入编译错误 |
| 脚本语言跳过 build | "Python 不需要编译" | lint/typecheck/语法检查等于编译验证 |
| 不主动提议测试 | "用户没要求测试" | 本 skill 要求你主动提议 |
| 修完直接 commit，跳过 build 和测试 | "改动很小，DI 注入而已" | 即使 DI 注入也可能拼错接口名、忘记注册 |
| 用 grep/读代码代替实际 build | "我看了注册代码，没问题" | 肉眼确认 ≠ 编译器确认 |
| 修改前不创建 checkpoint | "改错了我再手动改回来" | 手动回滚容易遗漏，git reset 一条命令干净回滚 |
| 直接在 main 上修改，不建分支 | "就改几行，不用分支" | checkpoint 提交污染 main 历史 |
| 后端接口修改后不实际调用验证 | "代码看着没问题，接口肯定通" | 序列化错误、路由冲突、中间件拦截，肉眼看不出来 |
| 测试通过后不清理调试日志 | "日志不影响功能，留着吧" | 调试日志污染正式日志、泄露内部状态、影响性能 |
| 思路错了不推翻 | "已经花了很多时间" | 沉没成本谬误——错的思路越早放弃越省时间 |
| 试错式修复 | "我先试试，不行再说" | 试错式修复比诊断慢得多 |
| 失败 3 次还继续修 | "再试一个方向" | 3 次还不行 = 架构有问题 |
| 一次改多个地方 | "这几个改动互不相关，一起测省时间" | 出了问题无法定位是哪个改动的锅 |
| 编译通过后不实际运行 | "编译都过了，肯定没问题" | 编译通过 ≠ 逻辑正确 |
| 用单元测试代替实际场景复现 | "单元测试通过了" | 单元测试覆盖不了完整调用链路 |

## 红色警报

出现以下想法时，**立即停止**，回到步骤 2：

- "这个问题很简单，直接改就行"
- "原因很明显，不需要分析其他的"
- "我已经分析完了（但没输出给用户），直接修吧"
- "我先改着，用户有意见再说"
- "测不测都差不多"
- "之前的方法虽然不太对，但改改还能用"
- "build 等会再说，先看看逻辑对不对"
- "用户没说要测，我就不提测试了"
- "我 grep 过了，注册没问题，不需要 build"
- "改完了，先 commit 再说"
- "改动很小，肉眼看看就行"
- "不用 checkpoint，我记着改了什么"
- "推翻重来太麻烦，在这个基础上继续修修"
- "接口参数我都检查过了，不需要实际调"
- "我自己的环境跑不起来，让用户自己测就行"
- "调试日志留着也不碍事"
- "就改几行，直接在 main 上改得了"
- "已经修了 3 次了，再试一种思路"
- "这几个改动一起上，测一次就行"
- "没时间对比了，直接猜一个方向改吧"
- "编译通过了，应该没问题了，让用户自己去跑一下看看"
- "我写了单元测试，测试通过了，就不需要实际运行了"
- "这个 bug 修了，虽然我没验证，但逻辑上是对的"
- "返回空列表也算正常，只要不报错就行"（如果用户预期是有数据，这就是 bug）

**以上任何一条都意味着你正在跳过诊断流程。**

## 速查：禁止事项

- 编译通过后不实际运行原始场景就声称"修好了"
- 用"单元测试通过了"来替代"实际运行验证"
- 验证时只确认"没报错"而不确认"结果正确"
- 不提供可复现的验证步骤就让用户自己去试
- 使用 Subagent 做 Bug 修复（Bug 修复必须由主控串行完成，保持连续上下文）
- 执行前不向 project-docs 请求上下文（违反强制契约）
- 执行后不向 project-docs 写回信息（违反强制契约）
- 绕过 project-docs 直接读写 `docs/junsi-dev-docs/` 下的文档
- 有 MCP 可用时不使用，手动维护文档
- 执行完成后不通过 MCP 写回信息

## 适用 vs 不适用

**适用：**
- 用户报告 bug、错误、异常行为
- Build 失败、测试失败
- 运行时崩溃或输出异常
- 用户说"修一下这个"
- 用户描述不符合预期的行为（无日志）

**不适用：**
- 用户只问"这段代码是什么意思"（纯解释）
- 用户明确说"直接改，我知道原因"
- 纯粹的代码格式化、重命名等机械操作
- 新增功能（非修复）—— 走 `requirements-driven-dev`
- 跨项目移植 —— 走 `code-migrater`

## 与现有 Skill 的关系

- **code-migrater**：跨项目/跨语言/跨框架移植，本 skill 不处理此类任务。
- **requirements-driven-dev**：新功能开发，本 skill 不处理此类任务。当用户同时说"加功能"和"报错"时，本 skill 让位于 RDD 中的 diagnose-before-fix 调用。
- **systematic-debugging**：已被本 skill 取代。本 skill 步骤 1-3 等价于 systematic-debugging 的诊断过程，步骤 4-8 覆盖修复和验证。
- **test-driven-development**：本 skill 的验证步骤遵循 TDD 精神，但专注于修复场景而非新功能开发。
- **verification-before-completion**：本 skill 的 build+验证步骤是其具体实现。
