# Diagnose Before Fix（证据优先）

## 铁律：断言背着举证责任

报告里的每一句结论，必须能回答「你怎么知道的」，三档标签不许含糊：

| 标签 | 门槛 | 例 |
|:---|:---|:---|
| **已证明** | 有可运行证据：测试失败输出、curl 响应、panic 堆栈、编译错误 | 「实测：HTTP 500，body 含 timeout」 |
| **已读证** | 读了代码确认逻辑成立，但没执行 | 「`getProgress` 从不读 `error` 字段」 |
| **潜在** | 逻辑上成立，但当前调用路径够不到 | 「直连 API 会踩到，当前 UI 恰好传值避开」 |

- 宁可标「潜在」也不谎报「已证明」；把「已证明」说成「可能」同样会埋真 bug。
- 证据一旦失效**主动撤回**：grep 无输出 ≠ 证明不存在，先确认日志走哪个通道。
- 也要说「查了没问题的」：列出检查过且安全的点，界定审查边界，让人知道是"查过"而非"漏了"。

## Gate 0：远程更新预检（动手修前必做）

在正式进入 8 步排查前，先确认该 bug 是否**已被上游最新版修复**，避免重复排查/重复修：

- `git fetch` 拉到最新远程，`git log origin/<分支>` 看近期提交，重点查 `CHANGELOG`/`Release Notes`/commit message 是否已提到本 bug（错误信息、症状、相关模块）。
- 可 `web_search` 查上游 issue/PR/发布说明确认。
- **若已修复/已合入**：不要重复修。提示用户"该问题已在版本/提交 X 修复，建议升级/拉取新版本"，并给出依据（提交号/PR/发布说明）。必要时协助做升级，而不是另写补丁。
- 若未修复或属本项目私有 bug → 正常进入下方 8 步排查。
- 在根因确认或最终报告里说明「已确认上游未修复，故自研补丁」或「上游已修复，改用新版本」。

## 流程（8 步，顺序执行）

1. **理解问题 + 立基线** — 读错误/日志/堆栈，`git log --oneline -20` 查近期改动。**依据路由层注入的范围，只读范围内代码**，不扫全文。**改前先跑 build/测试记下既有错误与 warning 数量**（无基线无法区分「这次改动引入」vs「本来就有的」，会把既存问题误报成新引入）。顺手确认所查代码属于哪个仓库（嵌套 .git / git check-ignore），跨仓库改动必须点明。此阶段不写代码。

2. **枚举原因（≥2 个，带证据标签）** — 每条原因引用代码位置 + 证据等级。**warning 是免费的 bug 索引**：先问每条 warning 在指什么（`unused variable` / `field never read` 常是参数被静默丢弃或路径漏接），不要当噪音清掉。怀疑行为但不确定 → **一次性探针**：写丢弃式最小验证（`cat > zz_probe` → 跑 → 删除），2 分钟把猜测变事实，**用完必须清理**。

3. **问方向** — 呈现原因（含证据等级），**用户确认后才改**。问+改在同一回复 = 没问。

4. **修复** — 改前先 `git stash` 或 `git commit -m "checkpoint:..."`。一次只改一个因素，改完 build 再改下一个。**改根因不改症状**：多个读取点都要钳位 → 所有权错了，该让唯一持有者钳一次，多处补丁是漏网的温床。优先级：不可远程触发的 panic / 让改动白做的缺陷 / 用户必然撞上的 bug > 洁癖式清理。顺手清相邻死代码可以，但发现范围外缺陷 → **报告 + 询问，不擅自修**。

5. **Build 验证** — 用项目 build 命令编译，**粘贴输出**。涉及 API 时实际调用端点验证。**回归测试必须验证「没修复时会失败」**：临时抽掉修复 → 测试必须 FAILED 且失败原因正是想守的那条 → 还原后全绿；**两边都过的测试等于零**。新测试要跑全量、跑多遍（单测过 ≠ 全量套件稳定，时序断言会抽奖）。

6. **原始复测** — 用与报告时完全相同的操作/输入运行一次，**粘贴输出**。实测细则：
   - 一次只动一个变量，重复取样量化（10/10 vs 0/10 是事实；「可能是抽风」是猜测）
   - 看副作用：接口一直报 downloading，但目标目录连 `.part` 都没有 → 一个字节没落盘，比任何进度数字有信息量
   - 结论匹配观测窗口：采样窗口太短就断言"卡死"是错判，先 `ls` 确认
   - 确认测的是哪个二进制：探一个只有新版才有的端点/字段
   - 别动用户运行环境：换端口起自己的实例，测完清理，确认用户实例还活着
   - 顺着因果链走到代码里：现象 → 机制 → 具体那一行丢了什么
   - 不报错 ≠ 正确，FAIL 则回步骤 2。

7. **建议测试** — 提议边界/异常测试点。

8. **收尾报告** — 按严重度排序，给出「我会先修哪几个」；每条给 `file:line` + 故障场景（什么输入 → 什么错误结果）+ 证据等级；显式写假设与未做的事（跳过了什么、还需要什么才能验证）；修复后给**修复前/后对比数据**，不只说"已修复"。**3 次失败 → 停止修代码，讨论架构**。

## 反模式清单

| 不要 | 要 |
|:---|:---|
| 「这里可能有并发问题」 | 跑一次证明，或标「已读证/潜在」 |
| 把既存 warning 当新引入的 | 先立基线 |
| 清掉 warning 让编译干净 | 先问每条 warning 在指什么 |
| 十个读取点各加一次钳位 | 让唯一持有者钳一次 |
| 加了测试就算完 | 验证它在没修复时会失败 |
| 单测过了就提交 | 全量套件跑多遍 |
| 凭记忆断言库行为 | 写探针实测 |
| 顺手修掉范围外的问题 | 报告并询问 |
| 重启用户的服务来验证 | 另起实例，用完清理 |
| 采样窗口内没看到就下结论 | 结论匹配观测窗口，看副作用 |

## 完成清单（全部为必须项，缺一项不得说"修好了"）

- [ ] 修改前已 checkpoint
- [ ] 修复前已立基线（既有错误/warning 数量）
- [ ] Build 通过（粘贴输出）
- [ ] 回归测试验证过「没修复时会失败」（粘贴输出）
- [ ] 原始场景复测通过（粘贴输出）
- [ ] 调试日志/探针已清理
- [ ] 根因确认后必须调用 `store-decision`（记录原因、修复方案、验证方法）
- [ ] 复测通过后必须调用 `save-progress`
- [ ] 涉及 API/行为变更必须调用 project-docs 的 `update_doc`/`create_adr`，禁止自己乱写文档

缺任何一项不得说"修好了"。

## Memory 集成

- **根因确认后** → **必须**调用 `store-decision`，记录原因、修复方案和验证方法
- **完成复测后** → **必须**调用 `save-progress`
- **感觉到降智/上下文将满** → 调用 `prepare-handoff` → 提示用户开新会话后继续
