# Junsi 开发工具包（Junsi Dev Toolkit）

## 概述

我是你的开发任务总入口。无论你想**移植代码**、**修复 Bug**，还是**添加新功能**，我都帮你路由到最合适的专用工具。

**核心原则**：如果某个子工具有哪怕 1% 的可能性适用于当前任务，你必须先路由到它。这不是建议，是强制。

## 路由规则（按优先级）

**在执行任何任务之前，必须先完成路由宣告**。

| 优先级 | 用户意图判断 | 路由到 | 说明 |
|:---|:---|:---|:---|
| 最高 | 含"移植/迁移/migrate/port/跨项目/跨语言/跨框架" | `./code-migrater/SKILL.md` | 完整移植流程 + Subagent 集群 |
| 次高 | 含"报错/不对/不工作/返回错误/显示不对/空列表/崩溃/白屏/不生效" | `./diagnose-before-fix/SKILL.md` | 诊断 + 修复 + 强制行为回测 |
| 中 | 含"文档/规范/ADR/架构/设计/API规范/编码规范/UI/组件/调用规范/系统设计/决策记录/整理文档/生成文档" | `./project-docs/SKILL.md` | 通过 MCP Server 执行文档操作 |
| 最低 | 含"添加/新增/实现/加个/做一个"新功能 | `./requirements-driven-dev/SKILL.md` | 需求澄清 + 实现 + 验证（条件启用 Subagent） |

**如果同时匹配多个规则，取优先级最高者。**

## 工作流

### 阶段零：检测当前模式

在路由之前，先检测当前处于什么模式：

**Plan 模式的特征**：
- 你正在生成步骤列表而非直接执行工具
- 系统提示"计划模式已启用"
- 你无法修改文件或运行命令

**Build 模式的特征**：
- 你可以直接修改文件
- 你可以运行编译/测试命令
- 你处于普通对话模式

**模式处理策略**：

| 当前模式 | 处理方式 |
|:---|:---|
| Plan 模式 | 执行**规划阶段**：分析问题→枚举原因→输出详细执行计划→**最后一步必须是"请用户切换到 Build 模式执行"** |
| Build 模式 | 执行**执行阶段**：按照计划修改代码→编译→验证→诊断→修复→测试（完整循环） |

**模式切换指引**（在 Plan 模式输出的末尾必须包含）：
```markdown
---
## 📌 下一步操作

以上是执行计划。请执行以下操作：
1. 确认计划内容
2. **切换到 Build 模式**（关闭 Plan 模式）
3. 回复"执行"或"开始"
4. 我将按计划逐步实施
---
```

### 0. 前置知识加载（通过 MCP 调用 project-docs）

**在输出路由宣告之前，必须通过 MCP 调用 `project-docs` 获取上下文：**

**调用方式**：
1. 使用 MCP 工具 `query_docs`，关键词根据任务类型自动提取：

| 任务类型 | 关键词 | 调用示例 |
|:---|:---|:---|
| 移植 | "架构设计,编码规范,技术选型" | `query_docs(keywords="架构设计,编码规范,技术选型")` |
| 修复Bug | "API规范,调用规范,错误码" | `query_docs(keywords="API规范,调用规范,错误码")` |
| 新功能 | "模块划分,API规范,UI/组件设计" | `query_docs(keywords="模块划分,API规范,UI/组件设计")` |
| 文档操作 | 直接路由，跳过本步骤 | 不调用 |

2. 将查询结果缓存，用于后续注入。

**输出方式**（对用户透明，自动执行）：
```markdown
📚 **已通过 MCP 加载项目知识**
- 调用工具：`project-docs.query_docs`
- 关键词：{keywords}
- 匹配文档：{N} 篇
- 关键约束：{摘要}
```

**如果 MCP 调用失败或无响应**：
- 记录错误信息
- 提示用户："MCP Server `project-docs` 未响应，请检查是否已启动。任务将继续但缺少项目知识上下文。"
- 继续执行但不注入知识

### 1. 路由宣告（强制）

在处理任何任务之前，你必须输出：

```markdown
## 路由宣告
- 检测到意图：[移植 / 修复Bug / 新功能]
- 匹配规则：[具体关键词]
- 路由到：`./[子工具名]/SKILL.md`
- 当前 Plan 模式状态：[已关闭 / 降级策略运行中]
```

**在输出路由宣告之前，禁止**：
- 写代码
- 提出实现步骤
- 审查代码
- 写测试
- 询问执行细节

### 2. 分发执行（含 MCP 注入 + 强制写回）

**第一步：通过 MCP 注入上下文**
- 将用户原始输入 + `query_docs` 结果一并传递给子工具：

```markdown
[用户原始输入]

## 📚 注入的项目知识（通过 MCP 从 project-docs 获取）

{query_docs 返回的文档摘要}

**执行本任务时，必须遵守以上规范/决策/架构信息。**
```

**第二步：子工具执行**
- 子工具按自身流程执行任务。

**第三步：强制写回（通过 MCP，执行完成后必须执行）**
- 任务完成后，路由器必须调用 `project-docs` MCP 工具更新文档：

| 任务类型 | 调用的 MCP 工具 | 参数 |
|:---|:---|:---|
| 移植完成 | `create_adr` 或 `update_doc` | 记录架构变更 |
| 修复完成 | `update_doc` | 如有 API/逻辑变更 |
| 新功能完成 | `update_doc` | 更新模块划分/API列表 |

**写回示例**：
```
调用 MCP 工具：project-docs.update_doc
参数：{
  "doc_path": "2-架构设计/模块划分.md",
  "content": "新增模块：Export 模块，负责数据导出功能",
  "change_description": "新增导出功能后更新模块划分"
}
```

**禁止行为**：
- 不调用 query_docs 就分发任务
- 调用后不注入结果
- 执行完成后不通过 MCP 写回文档

### 3. 子工具执行期间的路由静默

当一个子工具正在执行时，其他子工具**自动静默**。若用户尝试切换任务：
- 检查是否存在 `CHECKPOINT_*.md` 或 `VERIFICATION_LOG.md`。
- 若存在 → 提示"检测到未完成的任务，是否继续？"。

### 4. 路由日志

执行后，在项目根目录生成 `.toolkit_routing.log`。

## 子工具列表

| 子工具 | 路径 | 触发条件 |
|:---|:---|:---|
| `code-migrater` | `./code-migrater/SKILL.md` | 移植任务 |
| `diagnose-before-fix` | `./diagnose-before-fix/SKILL.md` | Bug 修复 |
| `requirements-driven-dev` | `./requirements-driven-dev/SKILL.md` | 新功能开发 |
| `project-docs` | `./project-docs/SKILL.md` | 文档管理（知识中枢） |

## 禁止事项

- 路由器不得自行执行业务代码修改
- 路由器不得绕过子工具直接输出结果
- 路由器不得同时运行多个子工具
- **在路由宣告之前，禁止做任何任务相关工作**
- **Plan 模式下，禁止一次性规划超过 3 步**
